Opening Git Bash

not started

Git Bash is a terminal application: a window where you type commands instead of clicking icons. On Windows, open it from the Start menu after installing Git for Windows. On macOS or Linux, your regular Terminal app already speaks the same language.

When it opens, you'll see a prompt — something like student@laptop MINGW64 ~$ — waiting for input. That dollar sign is Git Bash saying "I'm listening."

# check that Git is installed and see its version git --version

Why it matters: git --version is a safe, read-only command — a good first thing to type in any new terminal. It confirms Git exists before you try to use it.

Staging changes

not started

Git tracks changes in two stops before they're permanent: your working folder → the staging area → a commit. git add moves changes into staging — think of it as loading items into a box before sealing it.

# check what's changed git status # stage one file git add notes.txt # or stage everything that changed git add .
Your turn

$
Why it matters: staging lets you build a commit out of only the changes you actually want to save — you don't have to commit everything you've touched at once.

Committing

A commit seals whatever is staged into a permanent snapshot, with a message explaining what changed. Good commit messages are short, present-tense, and specific.

Creating a branch

not started

A branch is a parallel line of history — a safe place to try something without touching main. git switch -c (or the older git checkout -b) creates a branch and moves you onto it in one step.

# create and switch to a new branch git switch -c feature-login # see all branches, * marks the current one git branch

Why it matters: branches are cheap and disposable in Git — that's the whole point. Real teams branch for every feature or fix so main always stays stable.

Merging locally

not started

Once work on a branch is finished, you bring it into another branch with git merge. You run merge from the branch that should receive the changes.

# go back to main first git switch main # merge feature-login into main git merge feature-login
Your turn

You're already on main. Merge the feature-login branch into it.

$
Why it matters: merging is directional. git merge feature-login while standing on main pulls feature-login's work in — it does not push main's work out to the feature branch.

Resolving a conflict

not started

If both branches changed the same lines, Git can't guess which version you want and marks a conflict directly in the file with <<<<<<< / ======= / >>>>>>> markers. You edit the file to keep what you want, delete the markers, then stage and commit it like a normal change.

# after editing the conflicted file by hand git add resolved-file.txt # finish the merge git commit
Your turn

You've just hand-edited index.html to fix a conflict. Stage that file to mark it resolved.

$
Why it matters: a conflict isn't an error you failed to avoid — it's Git correctly refusing to guess. Staging the fixed file tells Git "I've decided," and a plain git commit (no -m needed) completes the merge.

Connecting to a remote

not started

Everything so far has been local — living only on your machine. A remote is a copy of the repository hosted elsewhere, like GitHub. origin is just the conventional nickname for your main remote.

# link a GitHub repo as "origin" git remote add origin https://github.com/yourname/your-repo.git # confirm it's linked git remote -v

Pushing to the remote

not started

git push uploads your local commits to the remote. The first time you push a branch, add -u to set it as the branch's default upstream — after that, plain git push is enough.

# first push: set upstream too git push -u origin main # every push after that git push
Your turn

Push your local main branch to origin for the very first time, setting it as upstream.

$
Why it matters: -u (short for --set-upstream) links your local main to origin/main permanently, so future pushes and pulls know where to go without you repeating the branch name.

Cloning & pulling

not started

git clone downloads an entire remote repository for the first time, complete with history. git pull updates a repo you already have, fetching and merging any new commits from the remote.

# download a repo for the first time git clone https://github.com/adalovelace/notes.git # update an existing local repo git pull origin main
Your turn

You already have this repo locally. Pull the latest changes from main on origin.

$
Why it matters: pull before you start new work, every time. It's the single most common habit that prevents avoidable conflicts with teammates.

Full feature workflow: branch → commit → push → merge to main

not started

This is the workflow real teams use daily. Every step below is one you've already practiced — the only thing new is doing them in sequence.

1. branch off main for your feature git switch -c feature-navbar 2. do your work, then stage and commit it git add . git commit -m "Add responsive navbar" 3. push the feature branch to GitHub git push -u origin feature-navbar 4. on GitHub: open a Pull Request, review, then merge it into main (or, working locally instead of via a PR:) git switch main git pull origin main git merge feature-navbar git push origin main
